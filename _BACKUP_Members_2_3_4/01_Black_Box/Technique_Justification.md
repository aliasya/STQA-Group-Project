# Week 1 – Black-Box Test Design: Techniques, Partitions and Test Data (BACKUP – Member 2)

Test cases and results: `Black_Box_Test_Cases.md` (generated by `run_blackbox_tests.py`, 35 cases).

## 1. Technique selection

| Feature (REQ) | Technique | Why it fits |
|---|---|---|
| Registration (REQ-01) | EP + BVA | Two independent input rules with numeric ranges (3–20, ≥ 8). Defects cluster at range edges, and EP keeps the number of cases small |
| Registration uniqueness (REQ-01) | Decision table | Outcome depends on the *combination* of username valid / password valid / username taken |
| Login (REQ-02) | Decision table | Outcome depends on user exists × password correct |
| Task title (REQ-04) | EP + BVA | Valid / empty / whitespace classes; 1-char minimum |
| Urgency (REQ-09) | BVA + state transition | The rule is defined by date boundaries (today, +2, +3). As time passes a task moves through states |
| Filter / search (REQ-08) | Decision table | Three filters combine (category × status × search) |
| Task status / delete (REQ-06, 07) | State transition | Task has meaningful states: Open, Done, Deleted |
| Session (REQ-02) | State transition | Logged out ⇄ Logged in controls access to every page |

## 2. Equivalence partitions and boundary values

| Input | Valid partitions | Invalid partitions | Boundary values tested | Test cases |
|---|---|---|---|---|
| Username length | 3–20 | < 3, > 20 | 2, **3**, **20**, 21 | TC-BB-004–007 |
| Username characters | letters, digits, `_` | `-`, space, other symbols | – | TC-BB-001–003 |
| Password length | ≥ 8 | < 8 | 7, **8**, 9 | TC-BB-008–010 |
| Task title | ≥ 1 visible character | empty, whitespace only | 1 char | TC-BB-015–017 |
| Due date vs today (d = days) | none, d < 0, d = 0, d ∈ {1, 2}, d ≥ 3 | – (UI date picker prevents malformed dates) | −1, **0**, 1, **2**, **3** | TC-BB-018–023 |

Test data justification: every boundary is tested on both sides plus the boundary itself (3-value BVA). Values come from the spec text, not from the code, so off-by-one errors in the code are caught.

## 4. State-transition models

### 4.1 Task status

```
          toggle                 toggle
 [Open] ─────────► [Done] ─────────► [Open]
   │                  │
   │ delete           │ delete
   ▼                  ▼
 [Deleted] (final; edit URL redirects to list)
```

| From | Event | To | Test |
|---|---|---|---|
| Open | toggle | Done | TC-BB-029 |
| Done | toggle | Open | TC-BB-029 |
| Open | delete | Deleted | TC-BB-030 |
| Deleted | open edit URL | (stays deleted, redirect) | TC-BB-030 |

### 4.2 Urgency (as the due date approaches)

```
[Upcoming] ──(d=2)──► [Due Soon] ──(d=0)──► [Due Today] ──(d=-1)──► [Overdue]
                                    (any) ──done──► [Done]
```

Tested in TC-BB-031 by editing the due date to +3, +2, 0, −1. **Result:** `Upcoming → Due Soon → Overdue → Overdue`. The *Due Today* state is unreachable (DEF-013).

### 4.3 Session

`[Logged out] ──login/register──► [Logged in] ──logout──► [Logged out]`. Protected pages from Logged out → redirect (TC-BB-032).

## 5. Results summary

35 executed · 28 Pass · 7 Fail (80.0 %). Defects confirmed: DEF-008 (duplicate username, also found by M1), DEF-012 (8-char password), DEF-013 (due today = Overdue: 4 failing cases), DEF-014 (whitespace title, create + edit).

The design paid off: **all 7 failures sit exactly on a designed boundary or rule combination** (password = 8, due = today, username taken, whitespace class). Random testing would most likely have missed them.
